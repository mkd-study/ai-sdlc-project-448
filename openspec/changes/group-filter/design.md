# Design

## Context

Мотивация и область описаны в [proposal.md](proposal.md), поведение — в [спецификации](specs/employee-selection/spec.md). Дизайн нужен, поскольку изменение затрагивает две формы и общее согласование выбора с импортом.

`App.tsx` хранит `userId` и `serviceId`, отображает всех `config.users` и вызывает `checkAccess`. `PermissionsPanel.tsx` независимо хранит `subjectValue` и сервис, объединяет сотрудников и группы в поле «Кому выдать». `useSimulator` из `src/app/index.ts` владеет конфигурацией и заменяет её после успешного импорта. Сейчас локальные значения форм отдельно не согласовываются с заменой справочников.

Модель уже содержит `User.groupIds: string[]`. Проверенный импорт допускает несколько групп, повторение связей и пустые списки. Учебные данные содержат только по одной группе на сотрудника, поэтому для крайних случаев нужны отдельные тестовые конфигурации. Существующие спецификации `access-calculation` и `config-import` не требуют изменений.

## Goals / Non-Goals

**Goals:**

- Дать обеим формам одно правило отбора и нормализации выбранного сотрудника через слой `app`.
- Согласовать отображаемое значение, результат расчёта и получателя операции в том же состоянии интерфейса.
- Сохранить направление зависимостей `components → app → domain`, формат конфигурации и прежние операции.

**Non-Goals:**

- Переносить фильтры в `Config`, менять доменный расчёт или вводить глобальное состояние форм.
- Перестраивать смешанный список получателей в новый многошаговый интерфейс.
- Исправлять посторонние особенности разбора идентификаторов, импорта или хранения.

## Decisions

### Общая чистая логика в слое приложения

Добавить `src/app/employee-selection.ts` с чистой функцией согласования: на входе конфигурация, идентификатор группы и выбранного сотрудника; на выходе существующая группа либо пустое значение, упорядоченный список доступных сотрудников и допустимый идентификатор сотрудника либо пустое значение. Сначала проверяется наличие группы, затем фильтруется `config.users` по включению идентификатора в `groupIds`, затем проверяется выбранный сотрудник. Пустое значение обозначает «Все группы»; импорт запрещает пустые идентификаторы сущностей.

Экспортировать функцию через `src/app/index.ts`. Тип результата принадлежит слою приложения, существующие сущности переиспользуются. Функция не меняет конфигурацию и не обращается к хранилищу. Линейного обхода достаточно для текущего приложения.

Альтернативы: дублирование правил в компонентах допускает расхождения; размещение в `domain/access.ts` смешивает выбор интерфейса с расчётом прав. Общий UI-компонент необязателен: формы выбирают разные виды субъектов и имеют разное пустое состояние.

### Локальные независимые фильтры и согласованные действия

Добавить `groupId` отдельно в `App` и `PermissionsPanel`. При смене фильтра согласовывать выбор сразу и записывать сброшенное значение в состояние, чтобы оно не восстановилось при возврате фильтра. Выбранный сервис при таком действии сохранять.

При смене конфигурации использовать нормализованные значения уже для отображения, расчёта, доступности кнопки и обработчика выдачи; синхронизировать сохранённое состояние с ними. Одной проверки визуального значения недостаточно: скрытый идентификатор не должен остаться в обработчике. Нормализация после импорта также проверяет существование сервиса и группы-получателя. Повторное появление удалённых записей не восстанавливает старый выбор.

В форме выдачи сотрудник проходит общую проверку видимости, а группа-получатель проверяется только на существование. Выдача или удаление разрешения при прежних справочниках сохраняет оба фильтра и допустимые значения.

Альтернативы: общий фильтр связывает независимые действия; безусловный сброс при каждом изменении конфигурации мешает повторной выдаче и проверке доступа после удаления; автоматический выбор первого сотрудника может поменять получателя без решения пользователя.

### Элементы интерфейса

Использовать существующий `NativeSelect`. Подписи фильтров: «Группа сотрудников для проверки» и «Группа сотрудников для выдачи». Первым вариантом будет «Все группы», далее группы в порядке конфигурации. Существующие подписи и `data-testid` полей сотрудника, получателя и сервисов сохранить.

В «Кому выдать» оставить порядок: пустой вариант, отфильтрованные сотрудники, все группы. При пустой группе показать «В этой группе нет сотрудников»; это сообщение не блокирует выбор группы-получателя. При пустой конфигурации достаточно пустых вариантов и существующей блокировки действий. Нативные поля сохраняют клавиатурное управление и связанные подписи.

Альтернатива с фильтрацией всех получателей скрыла бы группы и ограничила текущую возможность выдавать групповые разрешения. Мультивыбор и поиск потребовали бы дополнительных правил и не входят в запрос.

### Расчёт и конфигурация остаются полными

Передавать в `checkAccess` только выбранного сотрудника и сервис, как сейчас. В `PermissionsPanel` передавать полную конфигурацию; фильтровать только варианты сотрудников, не список разрешений. Операции `grantPermission`, `revokePermission`, `exportJson`, `importJson` сохраняют свои контракты. Фильтры не записываются в localStorage и не экспортируются.

Альтернатива с передачей урезанной конфигурации в расчёт или панель может потерять независимые источники и скрыть разрешения, что противоречит требованиям безопасности.

### Проверка через поведение

Реализацию вести скиллом `tdd`: для каждого среза сначала воспроизвести недостающее поведение падающим тестом, затем добавить минимальную реализацию и выполнить рефакторинг. Проверки чистой функции покрывают членство, порядок, повторы связей и нормализацию. Тесты `App.test.tsx` и `Permissions.test.tsx` покрывают выбор через формы, независимость фильтров, сброс, выдачу сотруднику и группе, импорт и полный расчёт доступа.

Для импортов использовать существующий путь загрузки файла; тестовые данные подготавливать через экспорт и публичный вход `src/app`. Сравнивать экспорт и содержимое хранилища до и после фильтрации. Существующие тесты доступа, разрешений и импорта сохраняют роль регрессионных проверок; новые интеграционные сценарии добавляют активные фильтры.

## Risks / Trade-offs

- Скрытый получатель остаётся в состоянии → нормализованные значения используются и в отображении, и в обработчиках; тест проверяет блокировку выдачи и отсутствие самовосстановления выбора.
- Импорт сохраняет идентификаторы, но меняет членство → согласование выполняется по актуальной конфигурации, а тест импортирует новые связи с теми же идентификаторами.
- Пользователь принимает фильтр за ограничение прав → подписи говорят о сотрудниках; результат сохраняет источники из всех групп.
- Пустая группа смешивается с невозможностью выдать групповое разрешение → сообщение относится только к сотрудникам, группы-получатели остаются доступны.
- Фильтр забывается после перезагрузки → это выбранное поведение, сохраняющее текущий формат конфигурации; обе формы начинают с полного списка.

## Migration Plan

Миграция данных не требуется. После реализации выполнить полный набор проверок на Node.js 26 и снять скриншоты обеих форм с активными фильтрами для запроса на слияние. Изменение поставляется обычной сборкой статического приложения. Откат интерфейса и вспомогательного модуля не требует преобразования сохранённых данных.
